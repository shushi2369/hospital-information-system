# 性能压测报告（混合写链路）

> 测试脚本：`deploy/perf/perf_concurrent.py`（可复跑）｜ 环境：单机 Windows 演示环境（nginx + Spring Boot + MySQL 8 + Redis 同机）｜ 日期：2026-10-04

## 压测场景

**不是只读基准**——每个"事务"是一条真实门诊写链路：

```
建档 → 挂号（行锁配额校验）→ 接诊（状态机推进）→ 新增诊断 → 收费（资金事务：唯一索引+幂等）→ 待缴费列表读
```

并发工作线程各自独立执行 R 轮完整链路，覆盖挂号桶 (doctor, period) 6 组合。

## 结果

| 场景 | 总事务 | 成功 | 失败 | p50 | p95 | max | 吞吐 |
|---|---|---|---|---|---|---|---|
| 40 线程 × 3 轮 | 120 | **120** | **0** | 5.76s | 8.80s | 9.08s | 6.2 事务/s |
| 80 线程 × 2 轮 | 160 | **160** | **0** | 9.71s | 12.01s | 12.67s | 8.0 事务/s |

## 正确性观察（比吞吐更重要）

- **零失败**：并发写链路全程无 500、无死锁回滚、无业务拦截误伤——幂等组件、`uk_bill_visit` 唯一索引、患者行锁（防同患者并发双入院）、挂号行锁配额计数（防号源超发）在真实并发下无破洞。
- **零脏数据**：压测后跑 57 段一致性巡检（汇总=明细、状态机终态、费用标记）0 行输出。
- 单事务 p50 5.76s 是**6 个串行 API 调用**的总和（含 2 次资金事务），单调用约 1s——瓶颈在演示机单盘 MySQL 的同步刷盘，而非应用层锁竞争（吞吐随线程数 40→80 仍线性提升 6.2→8.0 佐证）。

## 容量边界（诚实清单）

- 演示环境单机，未做读写分离与连接池调优（HikariCP 默认配置）；
- 压测未覆盖长事务（手术全链路）与报表大范围聚合的并发混合；
- 集群部署需先解决 Redis 单点（见运维手册演练实录）。
