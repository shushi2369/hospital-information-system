# 实验手册（E0~E10）

> 所有请求基于 `http://localhost:8080/api/v1`。登录：`POST /auth/login {"username":"<账号>","password":"His@2026"}` → 响应 `data.token`，后续请求头 `Authorization: Bearer <token>`。
> 写操作（POST/PUT）需要请求头 `X-Idempotency-Key: <任意唯一串>`（A0004 = 缺幂等键）。
> 验证 SQL 一律用 `mysql -uroot -proot123 his`。

## E1 患者建档与 PHI 脱敏（课时 3）

0. 身份证后四位**每次实验换新**（如 `+当天日期`），否则第二步直接撞上一次实验留下的 B1001。
1. `POST /patients` `{"name":"张三实验","gender":1,"birthDate":"1990-01-01","idCardNo":"34010419900101<后四位>","phone":"138<后八位>"}` → 200，`data` 为建档号 P…（**注意：建档号 ≠ 数字 id，下一步挂号要用的数字 `id` 从第 3 步列表接口取**）。
2. 同 payload 换幂等键再发 → **B1001**（重复建档，按 `id_card_hash` 查重）。
3. `GET /patients?name=张三实验` → 记下列表项的数字 `id`；`phone` 为 `138****…`，`idCardNo` 为 `3401**********…`（脱敏）。
4. `GET /patients?phone=138<后八位前缀>` （前缀检索）→ 能命中。
5. SQL：`SELECT id,name,phone,id_card_no,id_card_hash FROM pat_patient ORDER BY id DESC LIMIT 1;` —— 库里也是脱敏/哈希态。
**思考题**：把脱敏从服务端挪到前端会漏掉哪些泄露渠道？

## E2 就诊状态机（课时 4）

1. cashier.li 用 E1 的**数字 id**（不是建档号 P…）→ `POST /registrations {"patientId":<数字id>,"doctorId":2,"regDate":"<今天>","period":1,"regType":1}`；响应 `data.regNo/queueNo`，`regId` 从 `GET /registrations?patientId=<数字id>&regDate=<今天>` 取。
2. dr.li `POST /clinic/visits/{regId}/start` → 200，返回 visitId。
3. 再次 start 同一挂号单 → **幂等返回同一 visitId**（不报错——防重复点接诊；B1004 只在"已退号/已完成"后出现，可退号后复验）。
4. dr.li 暂存病历 + 录诊断（E4 的 complete 前置）：`PUT /clinic/visits/{visitId}/record {"chiefComplaint":"咳嗽3天","presentIllness":"受凉后咳嗽"}` + `POST /clinic/visits/{visitId}/diagnoses {"diagnosisName":"实验诊断","diagnosisType":1}`。**此时就诊停留 20（就诊中）——E3/E4 都要在"就诊中"状态下做，complete 在 E4 末尾才执行。**
5. SQL：`SELECT id,status,registration_id FROM cli_visit ORDER BY id DESC LIMIT 1;`
**思考题**：start 接口并发的场景是什么（两个窗口同时点接诊）？靠哪一层保证只有一人成功？

## E3 处方-审核（课时 6）

1. dr.li `POST /clinic/visits/{visitId}/prescriptions` `{"items":[{"drugId":1,"dosage":"0.25g","frequency":"tid","usageRoute":"口服","days":3,"quantity":2}]}` → 响应 `data.prescriptionId` + `rxNo`。
2. pharm.zhao `POST /pharmacy/prescriptions/{prescriptionId}/review {"pass":true}` → 200。
3. 再次 review → **B4008**。
4. 此时尝试发药 `POST /pharmacy/prescriptions/{prescriptionId}/dispense` → **B4002"处方尚未收费"**——发药的前置是收费（先做 E4.1 收费再回来发药）。
**思考题**：为什么发药必须在收费之后（资金与库存的先后约束）？

## E4 收费、发药与退费规则（课时 7）

1. cashier.li `POST /billing/bills {"visitId":<id>,"payMethod":1}`（带幂等键 K1）→ 200，记录 billId。
2. **同 K1 重放** → 返回**首次响应**（快照），库里仍只有一张账单。
3. **同 K1、换 body 重放**（改 payMethod）→ **A0005**（摘要不一致防误用）。
4. 回到 E3.4：收费完成后发药 `POST /pharmacy/prescriptions/{prescriptionId}/dispense` → 200（FEFO 扣减批次）；再次 dispense → **B4003**。
   SQL：`SELECT batch_no, quantity, expiry_date FROM inv_inventory_batch WHERE drug_id=1 ORDER BY expiry_date;` 观察扣减的是最早效期批次（FEFO）。
5. **退费受整方约束**：此时退账单上任何一行（如挂号费）都会被 **B3003"处方药品费须整方退费"** 拦截——账单里存在已发药的处方时，退费必须先整方退药。
6. 已发药直接退药费 → **B3004"请先到药房退药"**。走正路：pharm.zhao `POST /pharmacy/returns/{dispenseOrderId}?reason=<退药原因>`（整方退药，库存回补）→ 再整方退费（勾上挂号费+全部药费明细）→ 200，账单全退（30）。
7. **B3005 演示**（用一个新的无处方就诊）：新挂号 → dr.li 接诊（就诊 20）→ cashier.li 收费（账单仅挂号/诊查费）→ cashier.li 退挂号费 → **B3005"就诊已开始，挂号诊查费不可退"**（挂号费只在**未接诊**时可退）。换 dr.li 试同一请求 → 被数据范围拦截（顺带验证）。
8. 全链收尾：dr.li `POST /clinic/visits/{visitId}/complete` → 就诊完成（30）。
   SQL：`SELECT status,refund_amount,payable_amount FROM bil_charge_bill WHERE id=<billId>;` 观察部分退 20 / 全退 30。
**思考题**：幂等键由客户端生成——恶意客户端每次换键重放会怎样？兜底在哪一层？

## E6 住院全周期与一日清（课时 9）

1. admin 准备空床：`GET /inp/beds?wardId=1&bedStatus=1`，无则 `POST /inp/beds {"wardId":1,"bedNo":"LAB-x","chargeItemId":10}`。
2. `POST /inp/admissions {"patientId":..,"deptId":1,"wardId":..,"bedId":..,"doctorId":2,"admissionType":1,"plannedDiagnosis":"实验","depositAmount":1000,"payMethod":1}`。
3. dr.li 开医嘱并执行 → 生成费用；admin `POST /inp/daily-fees/manual?admissionId=<id> {"feeType":1,"itemName":"实验护理","quantity":1,"unitPrice":50}`。
4. dr.li `POST /inp/admissions/{id}/discharge {"dischargeWay":2,"dischargeDiagnosis":"实验出院"}` → 状态 20（出院未结）。
5. cashier `POST /billing/admissions/{id}/settle {"payMethod":1}` → 生成账单，押金抵扣 → 状态 30。
6. SQL：`SELECT charge_status,COUNT(*) FROM inp_daily_fee WHERE admission_id=<id> GROUP BY charge_status;`（应全为 1）。
**思考题**：结算后我再补一笔手工记账会发生在哪个状态？系统如何防它被漏结？

## E7 手术槽位冲突（课时 11）

1. 复用 E6 的住院（**必须 status=10 在院**——若已按 E6.5 结算，重新办理一次入院）：dr.li `POST /ors/requests {"admissionId":..,"patientId":..,"surgeryName":"实验术式","diagnosis":"实验","plannedDate":"<今天>","anesthesiaMethod":1,"surgeryItemId":<cat9 项目id>,"anesthesiaItemId":<cat10 项目id>}`。
2. dr.li `GET /ors/requests?admissionId=<住院id>` 取**数字 id**（创建响应是 SS 单号串）→ `POST /ors/requests/{id}/review {"approved":true}`。
3. or.nurse `POST /ors/requests/{id}/schedule {"roomId":1,"surgeryDate":"<今天>","seqNo":1,"surgeonId":2}` → 记录首次结果（seqNo 上限 10，撞台 A0001 则 seq+1 重试）。
4. 新建第二台同槽位申请并排台 → **A0001"该手术间台次已被占用"**（若首台已完成则槽位已释放——先把它跑到 60 再试）。
5. SQL：`SELECT room_id,surgery_date,seq_no,slot_active FROM or_schedule ORDER BY id DESC LIMIT 2;`
**思考题**：slot_active 的设计让"历史槽位记录"和"占用判断"共存——为什么不留物理删除？

## E8 日结锁定（课时 12）

1. cashier `POST /billing/settlements {"settleDate":"<今天>"}` → 200（RJ 单）。
2. 同参数再发 → **B3006**。
3. 同账号再收费/退费 → **B3006"当日已日结"**；**换账号**（另一收费员或 admin）对**另一就诊**收费 → 正常（同账号对同一就诊则是 B3001 重复收费，先分清两个拦截码）。
4. SQL：`SELECT settle_no,total_charge_amount,total_refund_amount,net_amount FROM bil_daily_settlement WHERE settle_date=CURDATE();` 并用明细重算比对：
   `SELECT SUM(payable_amount) FROM bil_charge_bill WHERE cashier_id=<id> AND DATE(pay_time)=CURDATE();`
**思考题**：为什么锁定按（本人，当日）而不是全系统？

## E9 危急值闭环（课时 13）

0. **造一个危急值**（前置链，复用 E6 的住院）：dr.li 开检验医嘱（`POST /doc/orders` category=4）→ pharmacist 审核 → nurse 执行（自动生成 LIS 申请）→ lab.chen `POST /lis/specimens/collect?requestId=<id>` → `POST /lis/specimens/{id}/receive` → `POST /lis/results/entry {"requestId":<id>,"fetch":true}`（Mock 仪器结果含超阈值项，如白细胞计数>30）→ 自动生成危急值。
1. 查待处理危急值：`SELECT id,alert_no,status FROM alert_critical WHERE status=10 ORDER BY id DESC LIMIT 1;`（表名是 **alert_critical**）。
2. lab.chen `POST /alerts/{id}/notify` → dr.li `POST /alerts/{id}/confirm` → `POST /alerts/{id}/close {"handleNote":"已复测"}`。
3. 故意跳步（未通知直接 confirm）→ 拦截。
4. SQL：`SELECT status,notified_at,confirmed_at FROM alert_critical WHERE id=<id>;`
**思考题**：闭环率指标怎么算？为什么把"通知时长"而非"闭环时长"作为超时升级点？
