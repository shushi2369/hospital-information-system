# 实验手册（E0~E10）

> 所有请求基于 `http://localhost:8080/api/v1`。登录：`POST /auth/login {"username":"<账号>","password":"His@2026"}` → 响应 `data.token`，后续请求头 `Authorization: Bearer <token>`。
> 写操作（POST/PUT）需要请求头 `X-Idempotency-Key: <任意唯一串>`（A0004 = 缺幂等键）。
> 验证 SQL 一律用 `mysql -uroot -proot123 his`。

## E1 患者建档与 PHI 脱敏（课时 3）

1. `POST /patients` `{"name":"张三实验","gender":1,"birthDate":"1990-01-01","idCardNo":"340104199001011234","phone":"13800001234"}` → 200，`data` 为建档号 P…。
2. 同 payload 换幂等键再发 → **B1001**（重复建档，按 `id_card_hash` 查重）。
3. `GET /patients?name=张三实验` → 列表项 `phone` 为 `138****1234`，`idCardNo` 为 `3401**********1234`。
4. `GET /patients?phone=1380000` （前缀检索）→ 能命中。
5. SQL：`SELECT id,name,phone,id_card_no,id_card_hash FROM pat_patient ORDER BY id DESC LIMIT 1;` —— 库里也是脱敏/哈希态。
**思考题**：把脱敏从服务端挪到前端会漏掉哪些泄露渠道？

## E2 就诊状态机（课时 4）

1. cashier.li 建档（复用 E1 患者）→ `POST /registrations {"patientId":<id>,"doctorId":2,"regDate":"<今天>","period":1,"regType":1}`。
2. dr.li `POST /clinic/visits/{regId}/start` → 200，返回 visitId。
3. 再次 start 同一挂号单 → **B1004**（已退号或已就诊，不能重复接诊）。
4. dr.li `POST /clinic/visits/{visitId}/complete` → 完成就诊（30）。
5. SQL：`SELECT id,status,registration_id FROM cli_visit ORDER BY id DESC LIMIT 1;`
**思考题**：start 接口并发的场景是什么（两个窗口同时点接诊）？靠哪一层保证只有一人成功？

## E3 处方-审核-发药（课时 6）

1. dr.li `POST /clinic/visits/{visitId}/prescriptions` `{"items":[{"drugId":1,"dosage":"0.25g","frequency":"tid","usageRoute":"口服","days":3,"quantity":2}]}`。
2. pharm.zhao `POST /pharmacy/prescriptions/{rxId}/review {"pass":true}` → 200。
3. 再次 review → **B4008**。
4. pharm.zhao `POST /pharmacy/prescriptions/{rxId}/dispense` → 200（FEFO 扣减批次）。
5. 再次 dispense → **B4003**。
6. SQL：`SELECT bag_no... `（略）；`SELECT batch_no,quantity FROM wh... 药品批次表` 观察扣减的是最早效期批次。
**思考题**：如果两台发药机并发发同一批次的最后 3 盒，系统靠什么不超发？

## E4 收费幂等与退费规则（课时 7）

1. cashier.li `POST /billing/bills {"visitId":<id>,"payMethod":1}`（带幂等键 K1）→ 200，记录 billId。
2. **同 K1 重放** → 返回**首次响应**（快照），库里仍只有一张账单。
3. **同 K1、换 body 重放**（改 payMethod）→ **A0005**（摘要不一致防误用）。
4. dr.li 未开始就诊时退挂号费：`POST /billing/refunds {"billId":..,"details":[{"chargeDetailId":<挂号费明细id>,"refundQuantity":1}]}` → 200；就诊完成（30）后再退 → **B3005**。
5. 处方已发药后退药费 → **B3004**；部分退药费 → **B3003**（整方退）。
6. SQL：`SELECT status,refund_amount,payable_amount FROM bil_charge_bill WHERE id=<billId>;` 观察部分退 20 / 全退 30。
**思考题**：幂等键由客户端生成——恶意客户端每次换键重放会怎样？兜底在哪一层？

1. 新患者建档 → 2. 挂号 → 3. 接诊 → 4. 开处方（含药）+ 开检查申请 → 5. 药师审核 → 6. 收费（幂等重放验证）→ 7. 发药 → 8. 申请退费被 B3004 拦 → 9. 退药 → 10. 整方退费成功 → 11. 检查申请回写已执行 → 12. 全程 `SELECT` 留痕核对。

## E6 住院全周期与一日清（课时 9）

1. admin 准备空床：`GET /inp/beds?wardId=1&bedStatus=1`，无则 `POST /inp/beds {"wardId":1,"bedNo":"LAB-x","chargeItemId":10}`。
2. `POST /inp/admissions {"patientId":..,"deptId":1,"wardId":..,"bedId":..,"doctorId":2,"admissionType":1,"plannedDiagnosis":"实验","depositAmount":1000,"payMethod":1}`。
3. dr.li 开医嘱并执行 → 生成费用；admin `POST /inp/daily-fees/manual?admissionId=<id> {"feeType":1,"itemName":"实验护理","quantity":1,"unitPrice":50}`。
4. dr.li `POST /inp/admissions/{id}/discharge {"dischargeWay":2,"dischargeDiagnosis":"实验出院"}` → 状态 20（出院未结）。
5. cashier `POST /billing/admissions/{id}/settle {"payMethod":1}` → 生成账单，押金抵扣 → 状态 30。
6. SQL：`SELECT charge_status,COUNT(*) FROM inp_daily_fee WHERE admission_id=<id> GROUP BY charge_status;`（应全为 1）。
**思考题**：结算后我再补一笔手工记账会发生在哪个状态？系统如何防它被漏结？

## E7 手术槽位冲突（课时 11）

1. 复用 E6 的住院：dr.li `POST /ors/requests {"admissionId":..,"patientId":..,"surgeryName":"实验术式","diagnosis":"实验","plannedDate":"<今天>","anesthesiaMethod":1,"surgeryItemId":<cat9 项目id>,"anesthesiaItemId":<cat10 项目id>}`。
2. dr.li `POST /ors/requests/{id}/review {"approved":true}`。
3. or.nurse `POST /ors/requests/{id}/schedule {"roomId":1,"surgeryDate":"<今天>","seqNo":1,"surgeonId":2}` → 记录首次结果。
4. 新建第二台同槽位申请并排台 → **A0001"该手术间台次已被占用"**（若首台已完成则槽位已释放——先把它跑到 60 再试）。
5. SQL：`SELECT room_id,surgery_date,seq_no,slot_active FROM or_schedule ORDER BY id DESC LIMIT 2;`
**思考题**：slot_active 的设计让"历史槽位记录"和"占用判断"共存——为什么不留物理删除？

## E8 日结锁定（课时 12）

1. cashier `POST /billing/settlements {"settleDate":"<今天>"}` → 200（RJ 单）。
2. 同参数再发 → **B3006**。
3. 同账号再收费/退费 → **B3006"当日已日结"**；**换账号**（另一收费员或 admin）→ 正常。
4. SQL：`SELECT settle_no,total_charge_amount,total_refund_amount,net_amount FROM bil_daily_settlement WHERE settle_date=CURDATE();` 并用明细重算比对：
   `SELECT SUM(payable_amount) FROM bil_charge_bill WHERE cashier_id=<id> AND DATE(pay_time)=CURDATE();`
**思考题**：为什么锁定按（本人，当日）而不是全系统？

## E9 危急值闭环（课时 13）

1. lab.chen 登记通知 `POST /alerts/{id}/notify`（用前序 LIS 实验产生的危急值，或查 `SELECT id,alert_no,status FROM lis_alert WHERE status=10 LIMIT 1;`）。
2. dr.li `POST /alerts/{id}/confirm` → `POST /alerts/{id}/close {"handleNote":"已复测"}`。
3. 故意跳步（未通知直接 confirm）→ 拦截。
4. SQL：`SELECT status,notified_at,confirmed_at FROM lis_alert WHERE id=<id>;`
**思考题**：闭环率指标怎么算？为什么把"通知时长"而非"闭环时长"作为超时升级点？

## E10 综合大实验（期末）

**任务**：给定一名新患者，完成"门诊就诊→处方→收费→发药→收住院→手术（排台+核查+完成）→出院→结算→日结"全链路，并满足：
1. 全程零脏数据（`consistency_check.sql` 0 行）；
2. 至少主动触发并解释 5 个不同的业务拦截码；
3. 提交操作时间线表（每步：接口、操作人、返回码、单号）；
4. 答辩：任抽一个环节讲解"如果并发会怎样，系统靠什么兜底"。

**评分**：链路完整 40 ｜ 拦截码解释 20 ｜ 数据核对 20 ｜ 答辩 20。
