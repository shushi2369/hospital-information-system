# HIS 系统性 Bug 模式清单（34 轮查验沉淀）

> 来源：HIS 项目 34 轮系统化查验、100+ 真实缺陷的归类沉淀。
> 用法：代码评审时的固定检查项；每条含【机理】【本项目真实案例】【检查方法】。
> 核心认知：**这些模式在单接口测试中全部无法发现**——只有跨模块/跨数据形态/并发/真实浏览器测试才能暴露。

## A. 并发与一致性

### 1. 丢失更新家族（读-改-写无断言）
- **机理**：`updateById` 影响行数为 0（乐观锁冲突或状态已变）时静默成功，资金/状态字段丢失更新。
- **案例**：退费、押金、医嘱审核、退号、接诊、病案归档全部中招后统一修复。
- **检查**：所有读-改-写必须断言 `updateById()==1`；资金字段用 `setSql("x = x - " + n)` 原子递减或 `SELECT FOR UPDATE`。

### 2. 跨用户并发不受幂等头保护
- **机理**：`@Idempotent` 按 userId+key 隔离，防得住同一用户双击，防不住两名操作员同时操作同一业务对象。
- **案例（三十一轮）**：双护士并发执行同一医嘱执行单 → 重复计费 + 重复生成检验申请单；双窗口并发登记同一患者 → 双在院记录。
- **修复**：执行单条件更新（`WHERE status=1`）+ 行数断言；住院登记加患者行锁（先锁后预检）。
- **检查**：每个"读-判-写"问一句：两个不同账号同时到达会怎样？

### 3. 预检+插入必须有 DB 唯一约束兜底
- **机理**：应用层 selectCount 预检与 INSERT 之间是竞态窗口。
- **案例**：EMC 分诊、住院登记、会诊、公卫卡——逐个补唯一键或行锁。
- **检查**：`SHOW INDEX` 对照每个业务单据的防重维度；MySQL 无部分索引时用生成列（`CASE WHEN status=10 THEN patient_id END` 建唯一键）或行锁串行化。

### 4. 幂等失败必须释放锁
- **机理**：幂等组件在业务失败后不释放 key，同 key 重试永远被拒。
- **修复**：捕获业务异常后 `redis.delete(redisKey)` 再抛出。

## B. 时间与状态机

### 5. MySQL DATETIME(0) 四舍五入陷阱
- **机理**：`LocalDateTime.now()` 带纳秒写入 DATETIME(0) 按 .5 进位（23:59:59.7 → 次日 00:00:00）。
- **案例**：收费 `payTime` 进位导致账单漂移到次日日结窗口，财务对账差一笔。
- **修复**：时间基准入库前统一 `.truncatedTo(ChronoUnit.SECONDS)`；比较两侧同口径。
- **检查**：全库 grep `LocalDateTime.now()` 与 `truncatedTo` 数量比对，写时间的入口点逐个过。

### 6. 状态机转换方向与守卫顺序（直觉陷阱）
- **机理**：仅凭方法名推断状态流转（以为 approve 在 report 前），实际后端守卫相反。
- **案例（三十二轮）**：公卫卡真实流程是 report(10→20 上报登记) → approve(20→30 审核)，前端接反后 UI 实测立刻报"报告卡未上报，不能审核"。
- **检查**：接状态机页面**必须先读服务端方法体的守卫消息**，把守卫消息固化为 e2e 断言。

### 7. 惰性补建/对账循环的 N+1
- **机理**：`for each 记录: selectCount(exists)` 随历史数据线性增长，开发期数据少不可见。
- **案例**：病案惰性补建（0.68s→0.15s）、床位一览逐床 3 查（0.37s→0.07s）、收费待缴费列表 300 查。
- **修复**：一次 IN 拉全量已存在集合，内存比对后仅补建缺失；字典类查询提供批量方法（listXxxByIds）。
- **检查**：定时任务与列表页接口在"数据量 ×100"假设下重新估算查询次数。

### 8. 定时任务的边界与幂等
- **案例**：床位费日结用"任务时刻在院"口径；执行单生成用"先查后插+唯一索引"幂等；效期/过号任务用条件 UPDATE 天然幂等。
- **检查**：任务重跑一遍是否产生脏数据？任务执行瞬间业务并发到达会怎样（事务隔离）？

## C. 数据形态与设计承诺

### 9. 同一业务在不同数据形态下必须各测一遍
- **案例**：退费单 visit_id 可空（门诊）vs 非空（住院）——只测一种形态漏掉另一种的约束缺失。
- **检查**：每个带可空外键的表列出形态矩阵（门诊/住院/无关联）。

### 10. 设计承诺逐条对照实现
- **案例**：设计文档"24h 时限标记""频次白名单""床位费类别校验""FEFO 拨发缺口告警"均在查验中被发现未实现。
- **检查**：把设计文档中所有"自动/校验/标记/告警"字样的承诺列成清单逐条验证。

### 11. 实体字段与迁移同步
- **案例**：多次因迁移加列但实体缺字段导致编译/运行错误。
- **检查**：迁移加列 PR 必须同 PR 改实体。

### 12. 事件载荷字符串拼 JSON 必须转义
- **机理**：用户输入（reason/note/receiptNo/职称）直拼进事件 JSON，引号/换行破坏载荷。
- **案例（三十二轮）**：全库清出 7 处未转义（公卫回执号/职称/项目名/血袋号）。
- **修复**：共享 `JsonEscapeUtil.escape()`；数字拼接除外。

### 13. 驳回/差异类参数勿丢弃
- **机理**：审批接口的 reason 字段表里无列又不留痕 = 审计黑洞。
- **修复**：至少记入平台事件（plt_event_log）。

## D. 数据资产与版本

### 14. 已执行迁移不可触碰（checksum）
- **机理**：修改已执行迁移 → checksum 校验失败阻塞启动；WinSW 重试循环反复触发。
- **处置**：改 SQL → 删 flyway_schema_history 失败行 → 清半套 DDL 残留 → clean package → 重启。**每次失败重放都会留下已成功语句的残留，必须重新盘点全部相关对象。**

### 15. 运行库与源码迁移可能漂移
- **案例**：手工调优直接改过运行库（EXPLAIN 补索引），后来 codify 成迁移文件但从未部署——新 jar 首启即撞 `Duplicate key name`。
- **检查**：部署新版本前，`information_schema` 盘点与迁移文件的差异。

### 16. 多语句 SQL 脚本中途出错不回滚
- **机理**：`mysql -e "stmt1; stmt2; stmt3"` 逐条执行，语法错后后续不执行、前面已执行的 DDL 不回滚。
- **检查**：修复类脚本执行后必须逐条核对实际生效范围。

## E. 测试方法论

### 17. API 级 e2e 对 UI 零覆盖
- **案例**：`main.ts` 缺 `createApp` 导致全站白屏，十五轮 API 查验未发现；三个四期页面组件从未创建、菜单点击即 404，潜伏至三十二轮才被浏览器走查暴露。
- **修复**：新前端交付必须含真实浏览器走查；长期方案是 Playwright 全菜单 404 猎手（deploy/e2e/ui_smoke.py）。

### 18. 测试脚本自身的潜伏 bug 也要查
- **案例**：跨日搜台回退路径 datetime 用法错误（单套跑不触发）；对账明细被服务端分页封顶 200 而漏计；池耗尽时同一只血袋兼任两个对撞角色导致安全门禁自锁。
- **检查**：给测试脚本内的自动补建循环设上限；套件失败先怀疑测试数据/脚本，再怀疑被测系统。

### 19. 唯一索引不含状态列时的槽位永久占位
- **案例**：排台槽位 `uk_schedule_slot` 不含状态，已完成/取消行仍占位；e2e 复跑与"取消后重排"必须按递增槽位处理。
- **检查**：设计唯一键时先回答"这行删了吗？取消后还能复用吗？"
