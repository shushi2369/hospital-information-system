# 24 - 五期候选方案评估报告

> 版本：V1.0（2026-09-22）
> 性质：评估报告（案头工作，不依赖外部资源即可完成）
> 结论先行：**五个候选全部技术可行**，推荐启动顺序为 ①区域平台上报 → ②信创适配（摸底）→ ③血站专线（被动就绪）→ ④AI 赋能（A 类先行）→ ⑤互联网医院（合规立项先行）。首选 **区域平台上报**：外部依赖最轻、四期基础复用度最高、等评硬指标。

---

## 1. 评估背景与现状基线

### 1.1 系统现状

四期全量完成并通过 30 轮系统化查验（79 个真实缺陷修复，连续多轮零新缺陷，收敛态）。

| 维度 | 基线 |
|---|---|
| 业务覆盖 | 一期门诊闭环 → 二期住院闭环 → 三期 LIS/危急值/药库、手术/影像/五大中心、人事/物资/体检/CDSS/KPI → 四期输血/耗材批次/CDSS 全面化/互认/门诊RIS/法定上报/会诊/院感/不良事件 |
| 规模 | 18 个业务模块、271 个 REST 接口、103 张表 1333 列、Flyway V1~V36 |
| 技术栈 | Java 17 + Spring Boot 3.2 + MyBatis-Plus 3.5.5 + MySQL 8.0.36 + Redis 5.0 + Vue 3.4 + TypeScript + Element Plus + Vite 5 |
| 质量 | 八套 e2e + 单测 + 并发 + 回归 ≈ 560 项断言全绿；27 段孤儿引用扫描零发现 |
| 运维 | 一键部署、5 项健康告警、恢复演练 RTO=9s / RPO≤24h、渗透自查全过 |
| 运行时 | Windows 服务化（HIS-MySQL / HIS-Redis / HIS-Backend / nginx），当前为**纯内网部署**（localhost / 172.17.176.47） |

### 1.2 与五期相关的四期存量资产

五期候选的可行性判断，核心看四期留下了哪些可复用的"半成品"：

| 四期资产 | 对五期的意义 |
|---|---|
| 法定传染病上报闭环（pub 模块，填卡→审核→上报→反馈工作流 + PubService 单测覆盖） | **区域平台上报的天然宿主**——院内上报流程已跑通，缺的只是"上报到平台"的最后一公里 |
| 检验/检查结果互认标识（lis/ris） | 互联互通测评的硬指标之一，已提前落地 |
| 会诊（cnt）+ 院感 + 不良事件（ae） | 与区域协同（双向转诊、AE 上报、院感监测）直接相关的三个模块已数字化 |
| 输血闭环（血袋入库→配血→发血签收→床边双签→不良反应） | 血站专线只差"库外协同"，库内全流程已闭环 |
| CDSS 提示级规则引擎 + 开单 hook（REQUIRES_NEW 异常隔离） | AI 建议的**标准接入模式**：提示级、不阻断、人工确认 |
| 数据字典 103 表 1333 列全覆盖 | 按国家/行业标准（WS 445 等）做数据映射时不需要补数据资产盘点 |
| 密码强度 / Mass Assignment / SQL 注入 / XSS / PHI 渗透自查全过 | 对外暴露类候选（互联网医院）的安全底子 |

### 1.3 评估方法

对每个候选按七个维度评估：**业务/政策价值、现状基础、差距与建设内容、外部资源依赖、技术工作量、风险与对策、结论**。工作量按"人周"估算（1 人周 = 1 名全栈开发一周），外部审批/联调周期单列，不计入技术工作量。

## 2. 候选一：区域平台上报（互联互通）—— 推荐 P0

### 2.1 业务/政策价值：高

- 互联互通标准化成熟度测评（"互联互通四级甲等"）的硬指标：机构需按国家卫生信息标准向区域平台上报数据。这也是三级医院评审的常规要求。
- 传染病、慢病、住院病案首页等上报是法定义务，目前系统内闭环已有（pub 模块），但"到平台"仍靠人工二次录入/线下报送。

### 2.2 现状基础

见 1.2：pub 上报工作流 + 互认标识 + 数据字典全覆盖，是五个候选中存量基础最厚的。

### 2.3 差距与建设内容

| 建设项 | 内容 |
|---|---|
| 上报网关（新增 `gateway` 或扩展现有 pub 模块） | 从"院内上报工作流"升级为"上报中心"：统一管理各条线上报通道、报文生成、回执处理、失败重试、补报 |
| CDA 文档生成器 | 按 WS/T 445《卫生信息共享文档编制规范》生成 CDA 文档（首批只做平台准入要求的子集：传染病报告、出院小结/住院病案首页、检验报告、检查报告） |
| 消息传输 | HL7 V2 消息或平台指定的 WebService/REST 协议；传输加密；前置机对接 |
| 数据映射 | 103 表 → CDA/HL7 字段映射表（数据字典可直接支撑） |
| 脱敏与签名 | 上报纸化 PHI 脱敏规则；CA 电子签章对接 |

### 2.4 外部资源依赖（轻）

| 依赖 | 说明 | 拿到的难度 |
|---|---|---|
| 区域平台准入 | 卫健信息中心注册机构账号、分配机构 ID | 流程性审批，周期可控 |
| 平台接口规范 + 联调环境 | 各地平台提供规范文档与测试前置机 | 申请即可得 |
| 前置机 | 平台通常要求部署前置机（一台服务器 + 网络策略） | 采购/虚拟机即可 |
| CA 证书 | 电子签章用 | 常规采购 |

### 2.5 技术工作量：6-8 人周

CDA 生成器 2-3 人周；上报中心扩展与回执/重试 1-2 人周；映射与脱敏 1-2 人周；联调修复 1 人周（联调周期受平台排期影响，另行）。

### 2.6 风险与对策

| 风险 | 对策 |
|---|---|
| 平台接口规范各地不一，可能反复变更 | 上报中心做**报文适配层**（模板化），规范变更只改模板不改流程 |
| 上报数据质量（空值/编码不符） | 复用一致性巡检思路，上报前做"报文级预检"，失败项进补报队列 |
| 平台联调排期不可控 | 开发与联调解耦：先用平台测试前置机自测报文合规性 |

### 2.7 结论

**推荐立即启动。** 理由：① 等评硬指标，政策价值明确；② 四期 pub/互认基础直接复用，边际成本五者最低；③ 外部依赖最轻且全是流程性审批。下一步产出《25-区域平台上报网关设计》（需先拿到本地区域平台接口规范，设计文档可先完成协议无关的架构部分）。

## 3. 候选二：信创适配（国产化）—— 推荐 P1（摸底先行）

### 3.1 业务/政策价值：中-高

医疗卫生是信创替代重点行业，HIS 属于核心业务系统，国产化替代是政策趋势与院内信息化评级的相关项。

### 3.2 现状基础（天然优势）

| 组件 | 信创友好度 | 说明 |
|---|---|---|
| Java 17 + Spring Boot 3.2 | ★★★★★ | 字节码跨平台，鲲鹏/飞腾 + 麒麟/统信直接运行 |
| Vue 3 + Element Plus | ★★★★★ | 标准 Web，国产 Chromium 内核浏览器（奇安信、360）直接兼容 |
| MyBatis-Plus 3.5.5 | ★★★★ | SQL 集中可管理，方言替换面可控 |
| MySQL 8.0.36 | ★★ | **主要工作量所在**：需迁达梦/金仓/OceanBase |
| Redis 5.0（Windows tporadowski 版） | ★★ | 需换国产缓存或信创环境 Linux 版 Redis/TongRDS |
| WinSW + Windows 服务 | ★ | 需换 systemd / 国产集群管理 |

### 3.3 差距与建设内容

1. **数据库迁移**（核心）：
   - 103 张表 DDL 方言改写（AUTO_INCREMENT、DATETIME 精度、JSON 列、索引语法）；
   - Flyway V1~V36 全量移植为达梦/金仓版（32 个增量脚本，**必须整套重写，不能逐条翻译**——已执行迁移 checksum 不可动的教训在此场景同样适用：信创库从 V0 重建）；
   - SQL 兼容面清理：`DATE_FORMAT` / `IFNULL` / `GROUP_CONCAT` / `ON DUPLICATE KEY UPDATE` / JSON 函数 / 分页方言，用 MyBatis-Plus 多方言支持 + databaseId 分流；
   - **DATETIME(0) 精度行为差异**：本库历史踩过"纳秒进位"坑（时间基准统一 `truncatedTo(SECONDS)`），达梦/金仓的时间类型舍入行为不同，时间基准逻辑需全量回归。
2. **缓存与中间件**：Redis 协议兼容发行版通常零代码改动，但需注意命令兼容（本库曾踩 Redis 5 无 `GETEX` 的坑——SessionService 已回退为 get+expire 两步，天然规避了一类兼容性问题）。
3. **部署形态**：ARM 架构全量重编译（Maven profile 区分）、nginx → 国产化分支、WinSW → systemd、部署脚本（deploy.sh）出 Linux 版。
4. **回归**：八套 e2e 在信创库上全量重跑是验收标准。

### 3.4 外部资源依赖（中）

| 依赖 | 说明 |
|---|---|
| 国产数据库授权 | 达梦 DM8 开发版免费/试用，金仓有试用授权——**摸底阶段零成本** |
| 信创测试环境 | ARM 服务器或虚拟机（麒麟/统信）；摸底阶段可用 x86 + 达梦 Windows 版先做 SQL 方言摸底 |
| 正式实施需国产化硬件/OS 采购 | 由院方立项，不在技术侧控制内 |

### 3.5 技术工作量：8-11 人周

数据库方言摸底 1-2 人周（**可立即启动，零外部依赖**）；V1~V36 移植 4-5 人周；SQL 兼容改造 2-3 人周；环境适配与全量回归 1 人周。

### 3.6 风险与对策

| 风险 | 对策 |
|---|---|
| SQL 方言隐蔽差异（隐性函数行为、隐式类型转换） | 先建达梦影子库跑全量 e2e 摸底，差异清单驱动改造，避免"迁完再发现" |
| 双库并行期的一致性 | 摸底/实施期以 MySQL 为准生产库，达梦库仅测试，不双写 |
| 性能差异 | 迁移后重跑 perf_test.py 压测基线对比（当前核心查询 <100ms） |

### 3.7 结论

**摸底立即启动，实施待环境。** 建议动作：本地装达梦 DM8 开发版 → 空库跑信创版 V1 → 八套 e2e 摸底 → 产出《SQL 方言差异清单》。该摸底零外部依赖、零生产风险，且产出物直接决定正式实施的准确性。

## 4. 候选三：血站专线（血站信息系统对接）—— 推荐 P2（被动就绪）

### 4.1 业务/政策价值：中

库内输血闭环已数字化，但"库外协同"（向血站订血、库存查询、发血确认）仍靠电话+纸质。对接后实现订血、库存、发血全链路电子化，减少差错与等待。

### 4.2 现状基础

四期输血闭环完整：血袋入库→配血→发血签收→床边双签→不良反应上报，配血不相容硬阻断。缺的只是血站侧数据进出。

### 4.3 差距与建设内容

| 建设项 | 内容 |
|---|---|
| 血站接口客户端 | 血液库存查询、用血申请上报、血液预订、发血接收确认、报废/退回回报 |
| 血液条码对齐 | 血站条码（ISBT 128 / 各地编码）直读入库，替代当前演示血袋生成逻辑 |
| 网络通道 | 专线或 VPN 隧道至血站/省血液管理平台 |

### 4.4 外部资源依赖（强，且不受我方控制）

| 依赖 | 难点 |
|---|---|
| 血站侧接口文档与授权 | **无全国统一标准**，各地血站多为 WebService/HL7 v2 或省级血液管理平台统一接口，必须拿到对端文档 |
| 专线/VPN | 网络部门流程 |
| 对端联调排期 | 血站配合度决定周期，技术侧无法压缩 |

### 4.5 技术工作量：3-4 人周（五者最低）

接口客户端 1-2 人周；条码对齐与入库改造 1 人周；联调修复 1 人周。

### 4.6 风险与对策

| 风险 | 对策 |
|---|---|
| 接口协议不统一、规范滞后 | 客户端做协议适配层，接口文档到位前不开发 |
| 血站条码与院内血袋编码冲突 | 入库时双编码并存（院内 ID + 血站条码），四期血袋表可平滑加列 |
| 联调周期不可控 | 技术侧先行完成报文模拟器自测，对端到位后只做真联调 |

### 4.7 结论

**被动就绪，先发函后开发。** 技术难度五者最低，但强依赖对端。建议：向血站/省血液中心发接入申请 → 拿到接口文档前排期其他候选 → 文档到位后 1 个月内完成技术侧开发。

## 5. 候选四：AI 赋能 —— 推荐 P3（A 类场景先行）

### 5.1 业务/政策价值：中-高

AI 医疗政策面持续利好，但**辅助诊断类需要 NMPA 三类证**，周期以年计。因此评估将场景分两类：A 类（非诊断，低监管风险，可先行）、B 类（诊断相关，持证/采购成熟产品再接入）。

### 5.2 场景分级

| 级别 | 场景 | 依赖的现有模块 | 说明 |
|---|---|---|---|
| A1 | 病历质控（文书完整性/逻辑矛盾/缺项提醒） | doc 电子病历 | 把一致性巡检的规则思路智能化，输出质控提醒 |
| A2 | 病案首页编码建议（ICD 辅助） | inp 出院、病案 | 编码建议由病案员人工确认后采纳 |
| A3 | 检验结果智能解读文案 | lis | 危急值体系已有，AI 补充面向临床的解读草稿，报告人确认后发布 |
| B1 | 影像辅助诊断（"第二阅片人"） | ris | 需 NMPA 证，建议采购成熟产品后嵌入 RIS 报告流程 |
| B2 | CDSS 大模型化 | cdss | 现有规则引擎负责硬规则，大模型补充语义判断，混合架构 |

### 5.3 现状基础与接入模式

CDSS 已确立"**提示级 + 不阻断 + 异常隔离**"接入模式（开单 hook 用 REQUIRES_NEW 隔离异常，提示不拦截流程）。**所有 AI 能力一律沿用此模式**：AI 输出仅为提示/草稿，永远由人确认，这同时化解了幻觉风险与监管风险。

### 5.4 差距与建设内容

| 建设项 | 内容 |
|---|---|
| 模型接入层 | 统一 LLM 网关（商用 API 或本地部署），带脱敏过滤器——PHI 不得发送至无协议保障的外部服务 |
| A1 病历质控 | 出院/提交前异步质控任务 → 质控提醒列表（复用 ae/质控类页面模式） |
| A2 编码建议 | 病案首页编辑页嵌入"AI 编码建议"侧栏，采纳留痕 |
| A3 结果解读 | LIS 报告页"生成解读草稿"按钮 → 草稿 → 确认 |
| 评测集 | 每场景建 50-100 例评测集，上线前与人工结果比对 |

### 5.5 外部资源依赖（中）

| 依赖 | 说明 |
|---|---|
| 模型资源 | 商用 API（需签数据安全协议 + 脱敏）或本地部署（最低 1-2 张 24G 推理卡跑 7B-14B 量化模型，适合 A 类任务） |
| 医学语料/知识库 | ICD-10/手术编码库（有公开版本）；质控规则语料可用院内历史病历 |
| B 类如走自研 | 需 NMPA 三类证——**不建议自研，采购成熟产品** |

### 5.6 技术工作量：8-10 人周（A1+A2+A3）

模型网关与脱敏 2 人周；每场景 2 人周；评测 1-2 人周。

### 5.7 风险与对策

| 风险 | 对策 |
|---|---|
| 幻觉/错误建议 | 提示级+人工确认硬闭环（沿用 CDSS 模式）；评测集达标才上线 |
| PHI 出域 | 默认本地部署；走外部 API 必须脱敏 + 数据协议 |
| 医疗责任界定 | AI 输出永久留痕（采纳/拒绝），责任链与现有审核签发链一致 |

### 5.8 结论

**A 类三场景先行，B 类只做采购集成。** A 类不触碰诊断监管红线、复用 CDSS 接入模式，是 AI 落地性价比最高的路径。前提是先定模型资源（本地部署 or 合规 API），这需要一次院方决策。

## 6. 候选五：互联网医院 —— 推荐 P4（合规立项先行，开发并行）

### 6.1 业务/政策价值：最高（也是合规最重）

线上复诊、处方流转、药品配送、线上支付、报告查询——直接的业务增长点。但受《互联网医院管理办法》监管：**依托实体医院取得互联网医院执业许可（省级审批）**，通常要求等保三级、处方合规链路、药师在线审方。

### 6.2 现状基础

门诊全闭环（挂号→就诊→处方→缴费→取药→报告）接口化程度高，271 个 REST 接口大部分可直接被互联网医院网关复用；就诊历史数据可支撑"仅限复诊"守门（互联网诊疗不得首诊）。

### 6.3 差距与建设内容

| 建设项 | 内容 |
|---|---|
| 网络边界重构 | 当前纯内网 → DMZ + WAF + HTTPS 证书 + 前后端分离的安全暴露面设计；这是**与现状差距最大的一块** |
| 患者端 | 全新前端工程（小程序/公众号 H5）：实名注册、人脸核身、预约、复诊申请、在线支付、报告查询、满意度评价 |
| 医生端 | 现有工作台增加"互联网接诊"入口（复用门诊工作台组件） |
| 在线支付 | 微信/支付宝商户、支付对账、退费链路（院内退费闭环已有，需增线上退费原路返回） |
| 药师在线审方 | 新增药师审方工作流（处方提交→药师审方→通过后流转） |
| 处方流转/配送 | 处方流转平台对接或院内药房+第三方物流配送 |
| 合规链路 | 医生 CA 电子签名、复诊守门（依就诊历史校验）、诊疗留痕与时间戳 |

### 6.4 外部资源依赖（最重）

| 依赖 | 周期 |
|---|---|
| 互联网医院执业许可（省级卫健审批） | 1-3 个月起，且可能要求系统先具备基本能力 |
| ICP 备案 + 等保三级测评 | 备案 1 个月；等保测评 2-3 个月 |
| 微信/支付宝支付商户 | 2-4 周 |
| 短信/人脸核身/CA/物流 | 各 1-2 周采购接入 |
| 公众号/小程序主体认证 | 2-4 周 |

### 6.5 技术工作量：10-14 人周

网关与安全边界 2-3 人周；患者端 4-6 人周；支付与对账 2 人周；审方与处方流转 2 人周；合规链路 1 人周。

### 6.6 风险与对策

| 风险 | 对策 |
|---|---|
| 合规不通过返工 | **先立项拿审批口径，再定开发边界**：审批要求的清单逐项映射到系统功能 |
| 安全暴露面骤增 | 借鉴已通过的渗透自查基线，扩展为互联网侧专项渗透测试；PHI 分级出域策略 |
| 处方合规（首诊/复诊界定、药品目录） | 复诊守门硬编码 + 互联网处方药品目录白名单（另行维护） |
| 内外网数据交换安全 | 网闸/单向光闸或严格的前置库方案，按院方网络政策定 |

### 6.7 结论

**价值最高、前置最重，建议"合规先行、开发并行"：** 立即启动立项与牌照/等保申报流程（外部周期最长，先跑起来）；技术侧可与申报并行做协议无关部分（患者端原型、审方工作流、复诊守门逻辑），网络边界与支付等强外部依赖项在许可落地后实施。

### 7.3 五期通用前置事项

无论先做哪个候选，以下事项为公共基础，建议随首批项目一并落实：

1. **等保测评**：区域平台上报与互联网医院都需要；信创环境迁移也需要安全测评配套。当前渗透自查通过是自查基线，不等保。
2. **CA 电子签章**：上报签章、互联网处方签名共用一套 CA 基础设施。
3. **PHI 分级与出域策略**：AI 与互联网医院共用；当前系统全内网，无出域管控，需先立制度再谈技术。
4. **测试体系延伸**：五期所有新增能力沿用现行验收纪律（e2e 断言 + 单测 + 一致性巡检 + 实测验证），设计文档按现行 24 号系列编号续编。
