# 06 实施计划与验收对照

版本：V1.0 ｜ 依据：《医院信息系统技术指导文档》§5、§6、§7、§8、§9、§10

## 1. 阶段划分与工作包

按指导文档 §6 四阶段推进；每阶段结束执行一次完整回归（演示脚本《05》§5）与阶段验收，通过后方可进入下一阶段。

### 阶段一：基础底座（第 1~3 周）

| 工作包 | 内容 | 产出 |
|---|---|---|
| WP1.1 工程骨架 | 前后端工程初始化、docker-compose（mysql/redis/minio/backend/nginx）、Flyway 接入、统一响应/异常/错误码、traceId、Logback 脱敏 | 可启动的空系统 + V1__init_schema.sql（02 文档全量表） |
| WP1.2 认证与 RBAC | 登录/登出/改密、JWT+Redis 会话、菜单权限初始化（V2）、@PreAuthorize 与数据范围拦截、操作日志 AOP | 《04》权限矩阵全部落地 |
| WP1.3 基础资料 | 机构/科室/医生/药品/收费项目 CRUD（D-01~D-14） | 管理员可维护全部字典 |
| WP1.4 用户权限管理 | 用户/角色/菜单管理接口（S-01~S-09） | 角色权限矩阵可配置生效 |

**阶段验收（§6 阶段一）**：管理员可创建用户、角色、科室、医生和药品；无权限用户不能访问受限接口（自动化测试断言 403）；关键操作可查询日志。
完成定义：全部接口通过四类测试（§3）；演示：新建医生账号 → 绑定 DOCTOR 角色 → 该账号登录仅见医生工作站菜单。

### 阶段二：门诊闭环（第 4~7 周）

| 工作包 | 内容 | 产出 |
|---|---|---|
| WP2.1 患者中心 | 建档/查询/修改/补卡（P-01~P-05）、身份证加密与摘要、重复建档拦截 | 患者档案可用 |
| WP2.2 挂号就诊 | 挂号/退号/队列/过号任务（R-01~R-05）、号源与排队号 | 候诊队列正确流转 |
| WP2.3 医生工作站 | 接诊/病历/诊断/医嘱/处方/检查申请/提交（C-01~C-12）、处方作废、状态机全部校验 | 门诊医生全流程可用 |

**阶段验收（§6 阶段二）**：患者建档到医生提交就诊记录全程可完成；重复挂号（B1002）、重复提交（幂等）、未保存病历提交（B2003）均有明确提示；就诊状态流转正确（按《05》状态机逐态断言）。

### 阶段三：收费与药房（第 8~11 周）

| 工作包 | 内容 | 产出 |
|---|---|---|
| WP3.1 收费结算 | 待缴费汇总/收费/退费/日结（B-01~B-08）、charge_status 跨模块联动、金额重算 | 收费闭环 + 事务一致性 |
| WP3.2 药房库存 | 审核/发药/退药/入库/批次/流水/预警（F-01~F-11）、FEFO 拣批、过期任务 | 药房闭环 |
| WP3.3 一致性专项 | 发药/退药/退费/收费并发与回滚专项测试（重复发药、库存不足、半成功状态检测） | 一致性测试报告 |

**阶段验收（§6 阶段三）**：收费金额与费用明细一致；已发药处方不可重复发药（B4003，唯一索引兜底验证）；库存不足不能发药（B4004 且无半成功数据）；退费和退药均保留原始记录；日结金额可由明细复核（T-03/T-04 对账一致）。

### 阶段四：报表与交付（第 12~14 周）

| 工作包 | 内容 | 产出 |
|---|---|---|
| WP4.1 统计与导出 | T-01~T-05 报表、CSV 导出（字段完整、大数量分页流式导出） | 报表与明细可交叉核对 |
| WP4.2 备份恢复 | 每日备份脚本、binlog 保留、恢复演练手册 | 按文档可恢复并通过核心流程验证 |
| WP4.3 交付文档 | 部署手册（全新环境）、用户操作手册（按 5 角色）、OpenAPI 导出、测试报告与缺陷清单 | 交付物清单齐套（§4） |
| WP4.4 性能与安全验证 | 100 并发压测、越权扫描、脱敏核查、备份恢复演练 | 非功能验收报告（§7） |

**阶段验收（§6 阶段四）**：报表与业务明细可交叉核对；导出文件字段完整；按文档可在全新环境部署；备份数据可恢复并通过核心流程验证。

## 2. 最终验收对照（指导文档 §9）

最终验收 = 演示脚本《05》§5 在全新部署环境**连续 3 次**执行成功，核对数据、金额、库存、权限、日志结果一致且无阻塞缺陷。核对清单：

| 维度 | 核对方法 |
|---|---|
| 数据 | 三轮产生的患者/挂号/就诊/处方/发药/退药记录结构与状态一致 |
| 金额 | 每轮收费 118.20、退费 118.20、日结净额与明细一致（种子价格固定） |
| 库存 | 每轮发药后 998 → 退药后 1000，流水可追溯 |
| 权限 | 每轮抽查 4 类角色的越权访问均被拒（A0003） |
| 日志 | 每轮 10 类关键操作日志齐全且脱敏 |
| 缺陷 | 无阻塞/严重级缺陷；一般缺陷有排期 |

## 3. 每接口四类测试（指导文档 §5.6，强制）

| 类型 | 断言要点 | 示例（以发药 F-04 为例） |
|---|---|---|
| ① 成功 | 返回 OK，落库数据与响应一致，审计日志生成 | 发药成功，库存/流水/状态全部正确 |
| ② 参数错误 | A0001，中文逐字段提示，无脏数据 | 处方 id 不存在 / 请求体为空 |
| ③ 无权限 | 未登录 A0002、无权限码 A0003、数据越权 A0003 | 药师调医生接口；医生 A 发药他人队列（不允许的场景不存在，但接口仍校验归属） |
| ④ 重复提交 | 同幂等键返回首次响应；业务态非法时返回对应 B 码 | 同键重放返回同一发药单号；再次发药 B4003 |

测试实现：后端 Testcontainers（MySQL/Redis）+ MockMvc/RestAssured；用例编号 `{接口编号}-{类型①~④}-{序号}` 纳入 CI，合并前必须全绿。关键流程回归 = 《05》§5 演示脚本自动化版（Playwright UI 层 + API 层双份）。

## 4. 性能测试方案（指导文档 §7）

- 环境：test 环境独立部署，数据量预置：患者 1 万、挂号 5 万、处方 3 万、库存流水 10 万。
- 工具：JMeter；场景：① 100 并发混合浏览（队列/查询/报表）持续 10 分钟；② 50 并发混合提交（挂号/收费/发药，幂等键独立）持续 10 分钟。
- 通过线：≥100 并发用户稳定；核心查询 95 分位 < 2s；提交类 95 分位 < 3s；错误率 < 0.1%。
- 配套：慢查询日志核查（>1s 的 SQL 必须有索引解释或改写），连接池与 Tomcat 线程参数随压测调优并固化到配置。

## 6. 提交与合并规范（指导文档 §5.8）

提交说明统一模板：

```
[变更目标] 一句话说明业务目标
[影响模块] 基础资料/患者中心/挂号就诊/医生工作站/收费结算/药房库存/统计报表/权限审计
[数据库变更] 无 / V{n}__xxx.sql（说明）

```

合并前检查门禁：代码检查（Checkstyle + ESLint）、四类测试全绿、演示脚本回归通过、新增接口已登记《03》清单并补权限码与矩阵、OpenAPI 导出更新。

## 7. 风险与边界声明（指导文档 §10 重申）

1. 本系统一期定位为**产品原型、内部试点或教学演示系统**，不默认满足真实医疗生产环境的监管、医保、电子病历评级和医疗安全要求；正式上线前必须另行完成合规评估、渗透测试、灾备设计、接口联调、数据治理和医院信息科审批。
2. 支付、医保、检验/影像接口一期均为模拟实现，预留防腐层接口（`PaymentGateway` / `LabInterface` 等接口占位），二期对接生产平台时仅替换实现。
3. 明确不做范围见《01》§1.2，任何新增范围必须走变更评审并同步修订本设计文档包。
